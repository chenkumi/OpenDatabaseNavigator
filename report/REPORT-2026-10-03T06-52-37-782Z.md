# WSL keyring 安全儲存驗收

日期：2026-10-03。接續 WSL 修復報告；使用者已安裝並解鎖 keyring，提供 `gnome_libsecret`、available=true、roundtrip=true 的診斷結果。

## 重驗結果

- `npm run check:secure-storage`：backend=basic_text，available=false、roundtrip=false，exit 1。
- `npm run check:secure-storage -- --password-store=gnome-libsecret`：backend=gnome_libsecret，available=true、roundtrip=true，exit 0。
- 因預設桌面識別仍未選到安全 backend，正式啟動必須指定 `--password-store=gnome-libsecret`，或配置能讓該程序選用 libsecret 的桌面識別；僅安裝 keyring 不代表預設啟動已成功。

## 真正應用程式憑證保存驗證

使用隔離暫存資料與 profile，以一般 Electron 啟動方式執行建置後的正式應用，帶入 `--password-store=gnome-libsecret`。透過 Chromium CDP 附加自動化，不使用 Playwright Electron launcher。

驗證全部通過：

1. 繁中首頁正常載入。
2. 正式 `connection.save` IPC 成功保存隨機產生、非真實的測試密碼。
3. credentials.json 不含測試密碼明文。
4. save/list IPC 回應不暴露測試密碼。
5. 真正主程序 safeStorage 選到 gnome_libsecret，且可以解密保存的憑證。
6. 關閉並重新啟動同一隔離應用後，連線仍存在，憑證仍可正確解密。

沒有嘗試連接測試主機，沒有使用真實帳號或密碼。測試憑證、profile、輔助探測模組均放在隔離暫存目錄；測試完成後關閉 Electron 並清除。

## 測試工具差異

最初使用 Playwright `_electron.launch` 驗證密碼儲存時失敗。查閱本機 `node_modules/playwright-core/lib/server/electron/loader.js:70,92-95`，確認其 loader 強制 appendSwitch(password-store, basic)，覆蓋 args 中提供的 backend；當時真正 main process 的 getSwitchValue(password-store) 為 basic，safeStorage 為 basic_text。

這不是正式應用使用 libsecret 的失敗。改用一般 Electron spawn 加 CDP 附加後，正式應用保存與重新啟動解密均成功。不修改 Playwright 套件，也不降低應用的安全限制。

## 啟動方式

```sh
npm start -- --password-store=gnome-libsecret
```

開發模式可為該程序提供桌面識別：

```sh
XDG_CURRENT_DESKTOP=GNOME npm run dev
```

本次直接验收的是前者的一般 Electron backend 路徑；開發模式命令此次未重新驗證。WSL 新工作階段仍需確保 keyring 已解鎖；若再次無法保存密碼，先重跑指定 backend 的 check:secure-storage。

## 結論

原先「缺少／未解鎖 keyring」環境阻塞已解除，指定 libsecret 的正式程式安全憑證保存與重新啟動解密已驗收。預設無參數啟動仍選 basic_text，不宣稱它已可保存密碼。前次程式修復與測試結果保留；本次未修改程式碼，未 commit/push。
